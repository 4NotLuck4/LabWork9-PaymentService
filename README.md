# Лабораторная работа № 9. Сервис оплаты

Сервис № 3 реализован на C# (.NET 8) по шаблону Worker Service. Он получает данные заказа из Apache Kafka, имитирует оплату и публикует результат.

| Роль | Топик |
| --- | --- |
| Consumer | `order.created` |
| Producer | `payment.completed`, `payment.failed` |

## Запуск

Нужен .NET 8 SDK. В каталоге с проектом выполните:

```bash
dotnet build
dotnet run
```

По умолчанию используется брокер из задания `10.9.2.80:9092` и группа `payment-service`. Если на брокере отключено автоматическое создание топиков, заранее создайте три топика из таблицы. Если команда согласовала другой адрес, топики или группу, измените параметры в `appsettings.json`. Их также можно передать через переменные окружения, например `Kafka__BootstrapServers`, или при запуске:

```bash
dotnet run -- --Kafka:BootstrapServers=localhost:9092
```

Новая группа начинает чтение с самого раннего доступного сообщения. Для проверок можно указать отдельный локальный брокер или согласованные с командой тестовые топики. У сервиса и сидера в этом случае должны совпадать адрес брокера и входной топик.

## Предлагаемый JSON-контракт для команды

В `order.created` обязательны `orderId` (непустая строка) и `amount` (число JSON, сумма в основных единицах согласованной валюты). Для каждого нового заказа нужен уникальный `orderId`. Дополнительные поля можно передавать в том же объекте. Рекомендуемый Kafka-ключ — `orderId`.

```json
{"orderId":"order-101","amount":1500.00}
```

Сервис публикует результат с ключом `orderId`. Поле `paymentId` содержит UUID, `processedAtUtc` — время в формате ISO 8601 (UTC).

`payment.completed`

```json
{
  "orderId": "order-101",
  "paymentId": "203a0b81-f7f1-4a63-8f6a-5147eed03432",
  "amount": 1500.00,
  "status": "completed",
  "processedAtUtc": "2026-11-20T08:30:00+00:00"
}
```

`payment.failed`

```json
{
  "orderId": "order-102",
  "paymentId": "8a30eaae-b7fe-4d96-aac2-64dc264a3593",
  "amount": 0,
  "status": "failed",
  "processedAtUtc": "2026-11-20T08:30:01+00:00",
  "reason": "invalid_amount"
}
```

## Правила обработки

| Условие | Результат |
| --- | --- |
| `0 < amount ≤ Payment:MaxAmount` | `payment.completed` |
| `amount ≤ 0` | `payment.failed`, причина `invalid_amount` |
| `amount > Payment:MaxAmount` | `payment.failed`, причина `amount_limit_exceeded` |
| Некорректный JSON или отсутствуют обязательные поля | Сервис записывает предупреждение и продолжает чтение |

Лимит по умолчанию — 10 000. Сервис сохраняет результат по `orderId` в каталоге `payment-data` перед публикацией, а Kafka-смещение подтверждает после публикации и сохранения её отметки. Повторный `order.created` с тем же идентификатором использует сохранённый результат. Запускайте один экземпляр сервиса и сохраняйте каталог состояния между перезапусками. При переносе на другой брокер или набор топиков укажите отдельный `Payment:StateDirectory`.

Если процесс остановится после отправки результата в Kafka и до записи отметки на диск, результат может прийти повторно с тем же `paymentId`. Потребители могут использовать этот идентификатор для дедупликации.

## Проверка сидером

Оставьте Worker запущенным. Во втором терминале из каталога проекта выполните:

```bash
dotnet run -- --seed
```

Сидер публикует два события `order.created` с новыми идентификаторами при каждом запуске:

| Заказ | Сумма при настройках по умолчанию | Ожидаемый результат |
| --- | ---: | --- |
| `demo-ok-…` | 1500 | `payment.completed` |
| `demo-fail-…` | 0 | `payment.failed` с причиной `invalid_amount` |

Сверьте идентификаторы из вывода сидера с логом Worker. Если доступны утилиты Kafka, можно также прочитать результат напрямую из топика:

```bash
kafka-console-consumer.sh --bootstrap-server 10.9.2.80:9092 \
  --topic payment.completed --from-beginning --property print.key=true
```

Для отказа укажите `--topic payment.failed`. При запуске на локальном брокере передайте сидеру тот же параметр `--Kafka:BootstrapServers=localhost:9092`, что и Worker.

## Результат проверки

Проект собрался без предупреждений и ошибок. На локальном Apache Kafka 4.0.0 проверены оба события сидера, совпадение Kafka-ключей с `orderId`, успешная оплата на границе лимита и отказ при его превышении. Сообщение без суммы было пропущено, следующие заказы обработаны. После перезапуска повторные заказы с теми же идентификаторами не создали новых результатов. Учебный брокер `10.9.2.80:9092` из среды проверки был недоступен.
